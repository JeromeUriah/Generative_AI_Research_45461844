# Generative AI Research Project

## Project Overview

This repository contains the files used for our research project on **"Using Generative AI Tools - Boon or Bane."**

The repository is organised into separate folders for the literature review, quantitative analysis, qualitative analysis, reports, and other research materials. GitHub is used to help organise the project, track changes, and support collaboration between team members.

## Project Structure

```text
Generative_AI_Research_SID/
│
├── README.md
├── Project_logbook.txt
├── .gitignore
├── 01_Literature_Review/
├── 02_Quantitative_Analysis/
├── 03_Qualitative_Analysis/
├── 04_Drafts_and_Reports/
├── 05_Additional_Materials/
└── 06_Documentation/
```

### 01_Literature_Review

Contains research sources used for the literature review.

This includes:

* Journal articles
* Conference papers
* Books and notes
* Newspaper and online news articles

### 02_Quantitative_Analysis

Contains files related to the quantitative part of the study.

This includes:

* Survey questions
* De-identified survey data
* Cleaned datasets
* Python analysis scripts
* Data visualisations
* Quantitative analysis reports

### 03_Qualitative_Analysis

Contains files related to interviews and qualitative analysis.

This includes:

* Interview protocols
* De-identified interview transcripts
* Coding and analysis files
* Qualitative findings
* Data visualisations

Sensitive or identifiable participant information should not be uploaded to a public GitHub repository.

### 04_Drafts_and_Reports

Contains different versions of research documents.

Examples include:

* Research proposal drafts
* Conference paper drafts
* Final research report

Git version control can also be used to track changes made to these documents.

### 05_Additional_Materials

Contains supporting materials that do not fit into the other folders.

Examples include:

* Participant information sheets
* Presentation slides
* Diagrams
* Images and other media

### 06_Documentation

Contains documents that explain how the project is organised and managed.

Examples include:

* Data dictionary
* File naming guide
* Contribution guide

## File Naming

Files should use clear and descriptive names so that team members can easily understand their purpose.

For example:

```text
Survey_Data_Cleaned.csv
Survey_Analysis.py
Participant_01_Transcript.docx
Research_Proposal_Draft_v1.docx
Qualitative_Insights_Report.docx
```

Spaces should be avoided where possible. Underscores can be used to separate words.

## Version Control

Git and GitHub are used to keep track of changes made to the project.

Team members should create a separate branch when making changes instead of directly changing the `main` branch.

Example branch names include:

```text
survey-analysis
update-literature-review
qualitative-analysis
update-project-logbook
```

## Making Changes

Before starting work, make sure the local repository is updated with the latest version of the project.

After making changes:

1. Save the modified files.
2. Review the changes in GitHub Desktop.
3. Write a meaningful commit message.
4. Commit the changes to the branch.
5. Push the branch to GitHub.
6. Create a pull request.
7. Ask the code reviewer to review the changes.
8. Merge the pull request after it has been approved.

## Commit Messages

Commit messages should clearly describe what was changed.

Good examples include:

```text
Added cleaned survey dataset

Added initial survey analysis script

Updated qualitative interview coding

Added literature review articles

Updated Project_logbook with analysis progress

Resolved Project_logbook merge conflict
```

Avoid unclear commit messages such as:

```text
update

changes

fixed stuff
```

## Collaboration

For the collaborative Git activity, one team member will act as the **code reviewer** and two members will act as **code developers**.

The code developers will fork and clone the reviewer's repository. Each developer will create their own branch and make changes to `Project_logbook.txt`.

The developers will then commit their changes, push their branches, and create pull requests.

The code reviewer will review the pull requests before merging them into the `main` branch.

The activity will also include creating a merge conflict by having both developers edit the same line of `Project_logbook.txt`. The reviewer will resolve the conflict before merging the changes.

## Data Privacy

Research data must be handled carefully.

Identifiable participant information, signed consent forms, raw recordings, identifiable photos, and other confidential information should not be stored in a public GitHub repository.

Only de-identified or example research data should be uploaded unless the repository and storage method have been approved for sensitive research data.
